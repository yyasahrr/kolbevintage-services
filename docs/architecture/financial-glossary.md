# Financial Glossary (Phase 4.7.6)

Terms are defined **as they exist in this repository**. Where a term describes something Phase 4.8 will
introduce, it is marked *(4.8)* and its meaning is frozen here so the implementation cannot drift.
All amounts are integer IRR (`BIGINT` in PostgreSQL, `bigint` in TypeScript, decimal strings on the
wire). No floats, no FX.

| Term | Meaning in this repository | Owner | Not to be confused with |
|------|----------------------------|-------|-------------------------|
| **Order total** | `wholesale_order.grand_total`: the buyer's transaction amount at creation (Σ child items). The *buyer* owes this; no seller is entitled to it. | Orders | Payable (which moves with shipping fees), payout basis |
| **Child order** | `purchase_order`: one seller's part of a parent order. Carries `seller_id` and `supplier_id` (`NULL` ⇒ Kolbe first-party). | Orders | A separate buyer transaction (it is not; the buyer pays the parent) |
| **Kolbe first-party child** | Child whose seller is the singleton `seller_kolbe` (`type='KOLBE'`, `supplier_id NULL`). Kolbe sells its own goods: **no supplier payable, commission 0, excluded from settlement**. | Orders / Suppliers (seller table) | An "internal supplier" — there is no such supplier row |
| **Commercial terms snapshot** | The `issued` `wholesale_proforma` and its `wholesale_proforma_line` rows: `unit_price`, `quantity` (in the pricing unit), `line_total`, `currency`, `terms_snapshot`. Immutable once issued (DB trigger). | Payments | Live offer/tier prices (never retroactive) |
| **Pricing unit / pieces** | `pricing_unit` ∈ PIECE, PER_PIECE, PACKAGE, SERIES, BOX, CARTON, SET. `piece_quantity` is always pieces; `quantity` is in the selector unit. Since 4.7.6 the proforma line `quantity` is in the **pricing unit** (pieces for PIECE/PER_PIECE). `piecesPerUnit = piece_quantity / quantity`. | Orders / Pricing | — |
| **Payable (child)** | `wholesale_proforma.total_amount` of the active proforma = `items_total + shipping_total`. Changes only by superseding the proforma (late shipping fee). | Payments | Order total; entitlement |
| **Payment** | `payment` row (order-level): buyer's cash instruction/evidence (`transfer`, `online` via provider, …) with `status` pending → verified/failed/cancelled. **Payment ≠ entitlement.** | Payments | Allocation, release |
| **Verified payment** | `payment.status='verified'` after admin verification or provider success (webhook/reconciliation, amount+currency+reference checked). Terminal; later provider events are `already_final`. | Payments / Finance | A "captured" payout to a seller |
| **Payment allocation** | `payment_allocation` row: how much of one verified payment covers one proforma (child lineage). Deterministic, capped. **The only link from cash to a seller.** | Payments | Ledger entry |
| **Unallocated paid** | Σ verified payments − Σ active allocations of an order (overpayment or voided lineage). **Never supplier money**; refundable only by an order-scoped refund. | Payments | Supplier balance |
| **Cash covered (child)** | Σ verified active allocations to the child's proforma lineage ≥ child payable. | Payments (fact) / settlement-readiness (read) | Financial release |
| **Financial release** | `order_financial_release` row authorising fulfilment: `payment_verified` (cash), `credit_approved`, `cod_policy_approved`, `manual_authorized_release` (**no cash**). **Release ≠ cash.** | Payments (row) / Finance (decision) | Cash coverage |
| **Financial ledger (current)** | `financial_ledger_entry`: an **append-only cash-evidence journal** of the *order*: `payment_verified` IN (child `NULL`), `refund_completed` OUT. `SUM(IN) − SUM(OUT)` = net verified cash of the order after completed refunds. It is **single-entry**, **not double-entry**, **not a general ledger**, and **never a supplier balance**. | Payments | The 4.8 settlement subledger |
| **Refund** | `refund` (+ `refund_allocation` to source payments, `refund_line` item/quantity basis). Child-scoped refunds reduce exactly the cited child/item/quantity; order-scoped refunds may only return unallocated money (4.7.6). Statuses requested → approved → processing → completed / failed. | Payments (via Finance) | Cancellation; chargeback |
| **Refund line** | `(wholesale_order_item_id, quantity, unit_price, line_total)` priced from the active proforma line; cumulative quantity ≤ ordered. | Payments | A free-form amount |
| **Exception-linked refund** | Refund whose `fulfillment_exception_id` points to an exception **of the same child** (4.7.6 check). Convention (FROZEN until an RMA flow exists): exception-linked lines are *never-delivered* quantity; unlinked lines are treated as post-delivery reductions. | Payments / Fulfillment | Return shipment (does not exist yet) |
| **Fulfillment exception / replacement** | `fulfillment_exception` (child, seller, affected items, `buyer_resolution`) and `fulfillment_replacement_request` linking an exception to a **new** `wholesale_request` (⇒ a new order). Nothing transfers automatically. | Fulfillment | Refund |
| **Cancellation** | Child status `cancelled` (Orders) and/or proforma `voided` (Finance, only without verified allocation). Cancellation is **not** a payment, release, refund or settlement event; a paid cancellation needs an explicit refund. | Orders / Finance | Refund |
| **Shipment / delivered quantity** | `shipment` (status pending → ready → handed_over → in_transit → delivered / failed / cancelled) with immutable `shipment_item.piece_quantity`. Delivered quantity of an item = Σ `piece_quantity` over `delivered` shipments. Idempotent on replay. | Shipping | Order status `delivered` |
| **Status-only delivery** | `POST /supplier/orders/:id/deliver` (`OrdersService.deliverChildOrder`) moves the child to `delivered` with `metadata.trigger='orders.child_deliver'` and **no shipment quantity**. It is **not settlement evidence**. | Orders | Quantity-evidenced delivery |
| **Shipping fee** | `shipping_quote.amount` selected by admin/finance ⇒ proforma `shipping_total`. Charged to the buyer. Its **economic owner is undefined** today (only physical `shipping_responsibility` exists). | Shipping / Payments | Supplier revenue |
| **Tax** | `commercial_invoice.tax_total` computed only when an `active` + `VERIFIED` `VAT_RATE_PERCENT` exists; never in the proforma/payment obligation; **never supplier cash by default**. | Invoicing | Merchandise value |
| **Commercial invoice** | Immutable document per child (`subtotal`, `shipping_total`, `tax_total`, `grand_total`, hashes). Evidence, **not** a payout basis. | Invoicing | Proforma |
| **Compliance eligibility** | `getSupplierSettlementEligibility(supplierId)`: profile, approval, contract, verification, bank, holds ⇒ `{eligible, reasons}`. | Compliance | Payout permission (which also needs money facts) |
| **Economic entitlement** *(4.8 name: earned quantity)* | Per seller/child/item: value of quantity that is **paid (cash covered) and quantity-evidenced delivered and not refunded**. Today only *previewed* by settlement-readiness as `merchandiseEntitledPreview` — **NOT A SETTLEMENT BALANCE**. | none today | Payment, release, invoice total |
| **Settlement-readiness** | Read-only, admin-only diagnostic (`GET /admin/settlement-readiness/...`): economic basis, cash coverage, compliance, blockers (economic/configuration/compliance/payout), `sourceDataSufficient`, `readyForSettlementEngine`. Writes nothing. | settlement-readiness (owns no tables) | A wallet/earnings screen |
| **Commission** *(4.8)* | Kolbe's fee on a supplier's entitled value; basis configurable and **snapshotted per child**; default before configuration **0**; computed with `basisPoints(amount, bps, rounding)` (integer, explicit rounding). | 4.8 settlement | A platform-wide constant |
| **Supplier payable** *(4.8)* | Entitled value − commission − attributable adjustments, as **balanced postings** in the settlement subledger; never a mutable column. | 4.8 settlement | Ledger `IN − OUT` |
| **Pending earnings** *(user-facing, 4.8)* | Entitled value recorded but still inside the configurable hold. | 4.8 | — |
| **Available for settlement** *(4.8)* | Pending earnings whose hold elapsed and no blocker applies. | 4.8 | Withdrawable "wallet balance" (do not use that term) |
| **Settlement pending / Settled** *(4.8)* | A payout request accepted / a provider payout confirmed. | 4.8 | — |
| **Amount on hold** *(4.8)* | Value blocked by compliance/legal/dispute holds or negative carry-forward. | 4.8 / Compliance | — |
| **Withdrawal** *(4.8)* | A payout **request** of available settlement balance — never a transfer by itself. | 4.8 | Payout |
| **Payout** *(4.8)* | Provider-executed transfer to the supplier's verified bank destination; TxA→provider→TxB with reconciliation. | 4.8 | Withdrawal |
| **Chargeback / reversal** *(4.8)* | A provider fact that verified cash was pulled back. Not representable today; when introduced it is a new event, never an edit of the verified payment. | 4.8 / Payments | Refund |
| **Adjustment** *(4.8)* | Explicit, reasoned, balanced posting (admin override, post-settlement refund, rounding residue). History is never rewritten. | 4.8 | Editing a row |
