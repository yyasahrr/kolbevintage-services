# ADR-001: مهاجرت بک‌اند به Medusa v2 و بازنشستگی تدریجی Supabase

- **وضعیت:** اجراشده (فازهای ۱ تا ۵ فشرده شدند و در یک موج پیادهسازی کامل شد)
- **تاریخ:** ۱۴۰۵-۰۶-۰۳ (2026-08-25)
- **تصمیمگیرندگان:** مالک محصول، تیم فنی کلبه

## خروجی پیادهسازی (بهروزرسانی)

- پنج ماژول دامنه در `backend/src/modules`: `account` / `supplier` / `wholesale` / `purchase_order` / `retail` + پرووایدر `payment-zarinpal`
- حدود ۳۴ endpoint سفارشی: فروشگاه (`/store/kolbe/...`)، پنل ساپلایر و عملیات ادمین (`/store/kolbe/admin/...` با نقشسنجی اختصاصی)
- جریانهای چندماژولی با جبران خطا در `src/lib/kolbe-flows.ts` (ثبت/تأیید/لغو سفارش عمده، تحویل PO)
- هر دو فرانت به Medusa وصل شدند؛ `supabase-js` حذف شد و حجم bundle فروشگاه ~۵۰٪ و ساپلایر ~۴۲٪ کم شد
- چکاوت خرده دمویی با ثبت واقعی سفارش (`retail` module) جایگزین شد — ایراد P0 ممیزی بسته شد
- seed کامل E2E: `backend/scripts/seed.mjs` کل مسیر ساپلایر → کاتالوگ → VIP → سفارش → PO → تحویل را میسازد

## زمینه و مسئله

پلتفرم کلبه دو تجربه زنده دارد: فروشگاه خرده (دمو) و زنجیره عمده/VIP/ساپلایر (واقعی، روی Supabase با RLS و RPC تراکنشی). مقصد ۱۰۰ هزار کاربر تعیین شده و بستر فعلی (Supabase) قرار است ماندگار نباشد. **منطق کسبوکار ثابت است و تغییر نمیکند:**

1. پنل ساپلایر (عضویت، کاتالوگ، RFQ، تسویه)
2. خرید عمده توسط حسابهای VIP (حداقل سفارش، تأیید سفارش)
3. تأمین بازار عمده توسط ساپلایرها (سفارش خرید، آمادهسازی، ارسال، رهگیری)

سؤال: بک‌اند بعدی چیست؟

## گزینههای بررسیشده

| گزینه | شرح | نتیجه |
|---|---|---|
| **الف) Medusa v2** | پلتفرم تجارت متن‌باز خودمیزبان؛ کاتالوگ/سبد/سفارش/پرداخت native + B2B Starter | ✅ انتخاب شد |
| ب) بک‌اند دستی (NestJS + همان اسکیمای Postgres) | انتقال ارزان زنجیره B2B فعلی | رد شد: کل لایه تجارت خرده (سبد، پرداخت، کمپین، مرجوعی) باید از صفر ساخته میشد |
| ج) ماندن روی Supabase | بدون هزینه مهاجرت | رد شد: تصمیم کسبوکار برای خروج از Supabase قطعی است |

## دلایل انتخاب Medusa

1. **خردهفروشی ستون درآمدی آینده است** و مدوسا کل لایه آن را آماده میدهد؛ گزینه ب این لایه را چندماهه میکرد.
2. **B2B Starter رسمی** دقیقاً به دامنه ثابت ما نقشه میخورد: حساب شرکت/کارمند، لیست قیمت عمده، سبد خرید با گردش تأیید، فلوی Quote (معادل RFQ)، سفارش پیشنویس.
3. **هر ساپلایر = یک Stock Location**: موجودی چندانباره با رزرو، native است.
4. مقیاس ۱۰۰k کاربر با اجرای چندنمونه‌ای بدون state + Postgres/Redis مدیریتشده قابل پشتیبانی است؛ گلوگاه دیتابیس و CDN است نه فریمورک.

## بخشهایی که باید دستساز شوند (ریسک ثبتشده)

- مالکیت محصول به ساپلایر (Marketplace در core نیست) → ماژول `supplier`
- زنجیره سفارش خرید (PO) و گردش تأمین → ماژول `purchase_order` + workflow
- درگاه پرداخت ایرانی (زرینپال/...) → Payment Provider اختصاصی
- پنل ادمین مدوسا انگلیسی/LTR است → پنل فارسی فعلی حفظ و به Admin API وصل میشود
- زیرساخت: میزبانی Node + Redis + Postgres + مانیتورینگ (Medusa Cloud با توجه به تحریمها گزینه نیست)

## پیامدها

- تا ۴ ماه فیچر جدید تجاری منتشر نمیشود (تونل مهاجرت).
- **هیچ کد بک‌اند جدیدی روی Supabase نوشته نمیشود** — هر خط جدیدش دورریز است.
- فرانتاند فروشگاه و پنل ساپلایر بدون بازنویسی میمانند و مرحلهای به Store/Admin API مدوسا وصل میشوند (الگوی strangler).
- دادههای عملیاتی (حسابها، سفارشها، کاتالوگ ساپلایر) با اسکریپت انتقال به اسکیمای مدوسا مهاجرت میکنند.

## معیارهای بازگشت تصمیم

اگر در بازه فاز ۱-۲ مشخص شود که خردهفروشی در ۱۲ ماه آینده جدی نیست، این ADR با ADR جدید بازنگری میشود و مسیر گزینه ب (بک‌اند نازک روی همان دامنه B2B) جایگزین میگردد.
