# Phase 5.4 feature-preservation and parity mapping

This audit maps the existing storefront/admin capability surface to the new CMS authority without changing frontend layout, color, typography, theme, components, or user experience. The frontend was intentionally not visually modified in Phase 5.4.

| Existing capability / source | Existing behavior audited | CMS representation / preservation decision | Cutover rule |
|---|---|---|---|
| `frontend-next/storefront/siteSettings.ts`, `frontend-kolbe/src/siteSettings.ts` | `SiteBuilder`, hero studio, popup, banner, look, Instagram, countdown, footer, typography and legacy `kolbe-site-content-v3` state | Typed `cms_content_document` configurations plus page blocks: `HOME_CONFIGURATION`, `HEADER_CONFIGURATION`, `FOOTER_CONFIGURATION`, `HERO_CONFIGURATION`, `PROMOTIONAL_CONTENT_CONFIGURATION`; import utility maps legacy `site_setting` values with deterministic keys | Legacy localStorage/server reads can remain temporarily for compatibility, but published CMS revisions are the backend authority after frontend read cutover |
| `frontend-next/storefront/siteData.ts`, `frontend-kolbe/src/siteData.ts` | Main/utility navigation, styles/look labels, blog cards, footer links and catalog-facing references | `cms_navigation` and bounded `cms_navigation_revision`; `STYLE_LOOK`, `EDITORIAL`, and `INSTAGRAM_EDITORIAL` blocks reference owning catalog/article/media IDs without copying catalog truth | Navigation must use published CMS revision; catalog and pricing remain read-only domain owners |
| `HeroStudio.tsx`, `HomepageHero.tsx`, `heroTemplates.tsx`, `HeroCountdown.tsx` | Cover/split/mosaic/duo/minimal hero templates, media, overlay, CTA, title/subtitle colors and countdown | `HERO` block plus `HERO_CONFIGURATION`; `COUNTDOWN` block for reusable countdown placement; media IDs recorded in usage table | Renderer preserves existing template contract; content API supplies validated values only |
| `SiteBuilder.tsx`, `visualBuilder.tsx`, `SiteDesignCenter.tsx`, `DesignSystemStudio.tsx` | Homepage section order, campaign-facing visual configuration, style cards, product-card settings | Page `blocks` with stable `order`/`enabled`, typed configuration documents, `STYLE_LOOK`, `CATEGORY_GRID`, `NEW_ARRIVALS`, `BEST_SELLERS`, `TRUST` | CMS cannot persist Promotions/pricing rules or mutate design system code; campaign references are read-only references |
| `Blog.tsx` and legacy `BuilderPost` | Blog/article identity, slug, title, excerpt, cover, category, author, pinned/featured, rich body and read time | `cms_article`, immutable `cms_article_revision`, Persian-safe slug, structured rich body, SEO, controlled `cms_article_taxonomy` categories/tags, media usage | Public article endpoint returns only active article + current published revision; HTML/JS is not persisted |
| `Static.tsx` and static route pages | About/contact/FAQ/collection/editorial static pages and route identity | `cms_page` with `STATIC`, `LANDING`, or `EDITORIAL` type and normalized unique `routePath`; `CUSTOM_TEXT`, `MEDIA`, `CTA`, `EDITORIAL` blocks | Reserved application roots remain unavailable to CMS page identity; frontend route ownership is not stolen |
| `Legal.tsx`, compliance legal-policy pages | Legal policy display and acceptance flows | CMS may reference published Compliance policy content in future, but no legal-policy or acceptance rows are imported/owned here | Compliance remains the sole legal authority; CMS never creates competing acceptance/version semantics |
| `SiteHeader.tsx`, `WholesaleHeader.tsx` | Header brand, shop/nav links, search/account/wishlist toggles and visual states | `HEADER_CONFIGURATION` plus versioned CMS navigation; links are validated safe URLs and may point to existing app routes | No UI redesign; no public draft exposure |
| `SiteFooter.tsx` | Footer title, columns, contact details, newsletter/social links, appearance | `FOOTER_CONFIGURATION` with typed allowlist and safe social URLs | Notification delivery and newsletter subscription remain outside CMS |
| `PromoPopup.tsx` | Popup enablement, timing, layout, copy, image, CTA and coupon-facing presentation | `POPUP_REFERENCE` block or `PROMOTIONAL_CONTENT_CONFIGURATION`; coupon/promotion authority remains a read-only reference | CMS stores presentation only; Promotions owns eligibility/discount logic |
| `frontend-next/server/kolbe-api.ts` legacy `site_setting` writes/reads | Legacy server settings persistence and compatibility fallback | `CmsLegacyImportService`: dry-run report, deterministic idempotency, AuditService record, no update/delete | Legacy rows are not final CMS authority; no destructive migration is performed |
| Existing media URLs/public assets | Current image/video behavior in storefront | `cms_media_asset` metadata, magic-byte validation, checksum, size, archive and usage tracking; only local public storage is implemented | No Compliance storage reuse; no S3/CDN claim; existing static assets remain untouched |
| Existing Admin RBAC/Audit | Existing role and permission enforcement, audit trail | New CMS actions in `ADMIN_PERMISSION_ACTIONS`; controllers use `AdminPermissionGuard`; mutations call existing `AuditService` in transaction | No competing auth/audit infrastructure |
| Existing public storefront reads | Published visual behavior and compatibility | New public API only selects current published revisions; signed, target-bound preview is separate | No draft/status leakage and no client-provided identity authority |

## Preserved domains and deliberate exclusions

- Catalog product/category/collection data, Offers/pricing, Inventory, Orders, Payments, VIP, Supplier, CRM, Support, and Notifications delivery remain authoritative in their existing modules.
- CMS block payloads can reference those domains by stable identifiers and render read-only data, but CMS does not write their tables or replicate commercial/legal truth.
- The frontend source files listed above were audited and remain behaviorally available; no Phase 5.4 change edits their visual surface.
